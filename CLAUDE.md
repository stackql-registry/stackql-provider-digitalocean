# stackql-provider-digitalocean

Generates the `digitalocean` StackQL provider from DigitalOcean's public OpenAPI spec, and builds the Docusaurus microsite served at digitalocean-provider.stackql.io via GitHub Pages.

## Layout

- `provider-dev/downloaded/` - the raw DigitalOcean OpenAPI spec (`make download-spec`)
- `provider-dev/source/` - service-level specs produced by split + normalize (gitignored, regenerated)
- `provider-dev/config/all_services.csv` - the operation-to-resource mapping table (see below)
- `provider-dev/config/*.json` - servers, provider auth, service config (pagination + pushdown), and service name overrides passed to the generator
- `provider-dev/openapi/src/digitalocean/v00.00.00000/` - the generated provider (this is what gets published to the registry)
- `provider-dev/scripts/` - post-generation fixups (see below)
- `test/smoke/` - live smoke test (`smoke.sh [--live] [--read-only] [--region X]`)
- `website/` - Docusaurus 3.10.x microsite; docs under `website/docs` are generated by `make docs`
- `examples/stackql-deploy/digitalocean-web-server/` - example stackql-deploy stack

## Workflow

`make all` runs the full pipeline: deps -> download-spec -> split -> normalize -> mappings -> provider (incl post-process) -> test-readonly -> docs -> website. Individual targets exist for each step (`make help`).

Generation tooling is `@stackql/provider-utils` (>= 0.7.x), called via its package CLIs (`provider-dev-utils.mjs`, `docgen-utils.mjs`) wrapped as npm scripts. The `normalize` step (new in 0.7.x) replaces the old local `flatten_allOf.cjs` post-processing.

## Mapping rules (backwards compatibility)

`all_services.csv` is the contract: once a resource is published, its service, resource name, method name, and SQL verb must not change between releases. The `analyze` step (`make mappings`) preserves existing rows and only appends new unmapped operations - fill in `stackql_resource_name`, `stackql_method_name`, `stackql_verb`, `stackql_object_key` for the new rows only. Use `skip_this_resource` as the resource name to exclude an operation (only for operations that are dead upstream, e.g. `genai_create_model_api_key` which returns only 410).

Service name overrides (`svc-name-overrides.json`) map OpenAPI tags to services (tag names are lowercased with `-`, ` `, `.` -> `_`). Existing tag-to-service assignments must not change.

## Pagination and pushdown

`service-config.json` is injected as `x-stackQL-config` into every generated service doc:

- pagination: `requestToken {key: '', location: request}` + `responseToken {key: $.links.pages.next, location: body}` (DigitalOcean returns full next-page URLs; any-sdk replaces the whole request URL)
- `queryParamPushdown.top` maps SQL `LIMIT` to `per_page` (max 200)

WHERE-predicate pushdown is not wired because any-sdk only renders OData `$filter` syntax, which DigitalOcean does not accept. Do not put pagination config in `provider.yaml` - the provider-level fallback for request/response tokens is broken in any-sdk; service-doc level is correct.

## Named lifecycle operations (fabricated)

DigitalOcean has no PUT/PATCH on droplets and similar entities - mutations go through generic `POST <entity>/actions` endpoints discriminated by a `type` field in the JSON body. `generate-lifecycle-ops.mjs` (post-process step 3) fabricates one named exec method per action type on the entity resource itself, AWS-style:

```sql
EXEC digitalocean.compute.droplets.reboot @droplet_id='123';
EXEC digitalocean.compute.droplets.power_off_by_tag @tag_name='web-fleet';
EXEC digitalocean.compute.volumes.resize @volume_id='...', @@json='{"size_gigabytes": 10, "region": "syd1"}';
```

Covered resources: `compute.droplets` (16 by-id + 8 by-tag), `compute.images` (convert, transfer), `compute.reserved_ips` / `compute.reserved_ipv6` / `network.floating_ips` (assign, unassign), `compute.volumes` (attach, detach, resize), `storage.shares` (6 NFS actions). The generic `*_actions_post` methods remain for backwards compatibility and future action types.

Mechanics (all standard any-sdk features - see the script header): faux path keys `<real path>?__type=<action>` for uniqueness, `requestTranslate: drop_double_underscore_params` strips the discriminator from the wire, `request.base: '{"type": "<action>"}'` injects the body field (user params merge on top), and each faux op carries the variant-specific body schema with nothing required (so `@@json` works for complex params). Docs need no special handling - docgen documents the faux methods natively under Lifecycle Methods.

Gotchas learned the hard way:
- The faux op MUST declare a `requestBody` (even an empty-properties object schema) or any-sdk refuses to send the base body ("no request body for operation").
- Integer path params are re-typed as string on faux ops - path params are strings on the wire, and this sidesteps an any-sdk EXEC validation bug (`providerTypeConditionIsValid` accepts `int/int32/int64` but not OpenAPI's `integer`, so integer-typed `@params` never validate). Integer/boolean body params are still affected - pass those via `@@json`.

## Request body translation

The provider is generated with `--naive-req-body-translate`: every POST/PUT/PATCH method gets `config: {requestBodyTranslate: {algorithm: naive}}`, so INSERT/UPDATE columns bind to request body properties by their direct names (`name`, `region`, `size`, ...) with no `data__` prefix. Keep this flag on every regeneration - dropping it reverts to `data__`-prefixed columns and breaks every published INSERT example.

## Post-generation fixups (run automatically by `make provider`)

1. `restore-op-servers.mjs` - normalize strips operation-level `servers`. Serverless/batch inference operations (paths under `/v1/`) are served from `https://inference.do-ai.run`, and agent inference (`/api/v1/chat/completions`) from `https://{agent_url}` (server variable becomes a required query param). any-sdk resolves op-level servers ahead of the service root, so re-adding them post-generation routes these correctly. Dedicated inference (`/v2/dedicated-inferences`) stays on the main API host.
2. `fix-oneof-required.mjs` - normalize flattens top-level `oneOf` request bodies and unions the variants' `required` lists, which can make INSERT unroutable (e.g. droplet create ended up requiring both `name` and `names`). The script relaxes `required` to the intersection of the variants' lists (only ever removes, never adds).

## Testing

- `make test-readonly` - read-only smoke checks against the live API using the locally generated provider
- `make test` - adds a droplet + volume lifecycle (smallest droplet `s-1vcpu-512mb-10gb` in `syd1`, 1 GiB volume; costs under one cent; a cleanup trap prevents leaks)
- `make test-live` - same but against the latest published provider (`registry pull`)

Auth: `DIGITALOCEAN_TOKEN` env var, or a `KEY=VALUE` line in `.env` (gitignored). The smoke test loads `.env` itself.

Local provider testing installs the generated docs into `.stackql/src/digitalocean/` (repo-local approot) rather than using `registry pull`, because a pull resolves the published registry version, not the local build.

Windows note: run the smoke test as `MSYS_NO_PATHCONV=1 wsl bash /mnt/c/.../test/smoke/smoke.sh`. Do not inline `$VAR`-bearing commands through `wsl bash -c` from Git Bash - wsl.exe re-wraps the command in another bash layer which expands variables before your command runs (empty tokens, silent 401s). Script files avoid this entirely.

## Website

Docusaurus 3.10.x using the vendored shared config pattern: `yarn build`/`yarn start` first clone `github.com/stackql/docusaurus-config` into `website/.shared-config` (gitignored) via the `prebuild`/`prestart` hooks (requires yarn v1). `docusaurus.config.js` and `sidebars.js` are thin wrappers over `createConfig()` from the shared config; per-provider identity lives in `website/provider.js`. Keep `website/static/CNAME` = `digitalocean-provider.stackql.io`.

## Publishing

Push the `provider-dev/openapi/src/digitalocean` tree to `providers/src` in a feature branch of `stackql/stackql-provider-registry` (release flow in that repo's docs). The published version id (e.g. `v25.09.00345`) is assigned by the registry release process; the local tree stays at `v00.00.00000`.
